Module 1 of 6

Introduction to Agentic AI

Your first published agent

An agent is software that reads a request, decides what to do, and does it, rather than following one fixed script. You will build one that answers member questions about plan benefits, publish it, and chat with it from the class portal.

What you will be able to do

  • Tell an agent apart from a fixed automation, and name where each helps a health plan.
  • Stand up the lab and publish your first conversational agent.
  • Connect a model provider without ever putting a key in a browser.

Why it matters in a health plan

Members ask the same benefit questions every day. An agent that answers from approved plan language, and only from it, frees staff for the calls that need a person.

Reading the figure

  1. The member's question enters at Chat Input.
  2. The Prompt Template holds the instructions that set the agent's tone and limits (a 'system prompt').
  3. If you add a Knowledge Base, passages from plan documents are placed into the prompt first.
  4. The Chat Model writes the answer and Chat Output shows it.

How you build it

  1. Add Chat Input and Chat Output.
  2. Write the system prompt in a Prompt Template.
  3. Connect an OpenRouter chat model; keep the API key on the server, never in a browser.
  4. Optionally add a knowledge base of plan documents.
  5. Publish, then test PPO versus HMO questions across several turns.

Module 2 of 6

Components of an Agentic AI

Memory, variables and prior cases

A conversation is more than one question. This module gives the agent memory: the member says 'I have an HDHP' once, and a deductible question two turns later is answered for an HDHP without asking again.

What you will be able to do

  • Add memory to a model and control how much of the conversation it keeps.
  • Keep each student's conversation separate with a session id.
  • Use a knowledge base as memory of prior cases, and map a turn onto Observe, Orient, Decide, Act.

Why it matters in a health plan

A member should never have to repeat their plan type. Memory scoped to a session gives continuity without mixing people's data.

Reading the figure

  1. Each turn arrives at Chat Input and goes through the Prompt Template to the Chat Model.
  2. Message History holds the stored turns for this session, the last ten by default, and the model sees them.
  3. Every reply is stored too (the dotted arrow back), so the next turn can use it.
  4. A new session id starts a fresh history; that is how students never see each other's chats.

How you build it

  1. Add a Message History component next to the Chat Model.
  2. Keep a window of ten turns.
  3. Give every student their own session id, so conversations never mix.
  4. Ask "I have an HDHP", then "What is my deductible?" and watch it remember.

Module 3 of 6

Tool Use and MCP Servers

Looking things up, read only

Now the agent can act in the world, carefully. It gets two tools that read claim and prior-authorisation status from a practice service. The agent chooses the tool from the question itself; nothing is ever paid or changed.

What you will be able to do

  • Tell observation tools (read) from action tools (write), and why the class ships only the first.
  • Give an agent HTTP tools and watch it pick the right one from plain language.
  • Understand MCP as the standard way to offer tools, and when you would use it instead of a direct request.

Why it matters in a health plan

Reading status is the safest useful act an agent can take. Read-only tools with clear descriptions are how a health plan starts, before any tool that changes a record.

Reading the figure

  1. Chat Input brings the question to the Agent.
  2. The Agent decides: a claim question calls Claims Lookup, a PA question calls Prior Auth Lookup (dotted arrows are calls).
  3. Both tools read from the Mock Claims API, a practice service with fixture members.
  4. The Agent writes the reply, quoting the status it read, at Chat Output.

How you build it

  1. Add an Agent and connect Chat Input and Chat Output.
  2. Add two API Request components pointed at the mock service.
  3. Turn on Tool Mode on each and connect their Toolset port to the Agent's Tools port.
  4. Describe each tool as read-only in its description.
  5. Ask about member M1001 and prior-auth PA-9001.

Module 4 of 6

Building Agentic AI Applications

Intake that asks for what is missing

Real requests arrive incomplete. This module builds an intake flow that pulls the required fields out of a message, asks a clarifying question when something is missing, and submits only when everything is there.

What you will be able to do

  • Build a resilient intake: extract, validate, clarify, submit.
  • Route questions by intent (billing or clinical) on one canvas.
  • Validate formats such as a provider NPI, and fall back gracefully when extraction is weak.

Why it matters in a health plan

An intake that silently fails costs a phone call later. One that asks for the missing field finishes the job in the same conversation.

Reading the figure

  1. The message goes to Structured Output, which fills three required fields.
  2. Fields Missing is a decision: it checks whether every field is present.
  3. Missing something? Clarify asks for just that. Complete? Submit Intake posts the request.
  4. Either way the member gets a reply at Chat Output: a question or a confirmation.

How you build it

  1. Add Structured Output with the three required fields.
  2. Add a conditional router on "any field missing".
  3. On the missing branch, a chat model asks the clarifying question.
  4. On the complete branch, an API Request submits to the mock service.
  5. Test with the incomplete fixture and watch the clarify branch fire.

Module 5 of 6

Designing Collaborative Agents

A person approves before anything leaves

Some steps must wait for a human. The capstone drafts a denial appeal, pauses for a specialist, and submits only an approved draft. A rejected draft goes back for another pass, and the member sees a pending notice meanwhile.

What you will be able to do

  • Put a human decision in front of any external action.
  • Review and annotate what the agent did, from the message log.
  • Escalate when the tone turns angry, and show a waiting state while approval is pending.

Why it matters in a health plan

An appeal that reaches a payer is a real action with real consequences. The gate keeps people responsible for it while the agent does the drafting.

Reading the figure

  1. The case comes in at Chat Input and Draft Packet writes the appeal summary.
  2. Human Input is the gate: the flow pauses until a specialist chooses Approve or Reject.
  3. Approve goes to Submit Appeal; Reject (the dotted arrow back) returns to drafting.
  4. While the gate waits, Chat Output tells the member that review is pending.

How you build it

  1. Add a chat model that drafts the appeal packet.
  2. Add a Human Input component with Approve and Reject actions.
  3. Wire only the Approve branch to the submission request.
  4. Wire Reject back to the drafting model.
  5. Run it: the flow pauses at the gate and resumes without re-running finished steps.

Module 6 of 6

Ethics and Security

Audit what the agent keeps and may do

No canvas in this module. Students take a flow that already ran, export what it stored, and work through an audit: protected health information in prompts and logs, how much a tool is allowed to do, who may edit flows, and what leaves in an export.

What you will be able to do

  • Find PHI where it hides: prompts, retrieved chunks, conversation logs.
  • Judge tool scope: read-only against write, and the risk of too much agency.
  • Set roles, retention and export hygiene for a lab that holds member data.

Why it matters in a health plan

Every earlier module stored something about a member. This one makes sure the class can say what, where, for how long, and who can see it.

Reading the figure

  1. An Instructor Flow from an earlier module runs once more.
  2. Its Message Export, pulled through the Monitor API, is the raw material.
  3. Students work the Audit Rubric from that export.
  4. Findings: flagged fields, over-broad tools, retention gaps, keys in an export.

How you build it

  1. Run one earlier flow and export its session messages.
  2. Hand out the audit rubric.
  3. Flag every field that holds PHI and every tool that could write.
  4. Try red-team prompts against a flow with a write tool, and record the mitigations.
  5. Scan a flow export for keys before it goes into git.
