How the workflows coordinate

A chat message reaches an Agent, which calls tools, reads stored messages and answers, while flows are also served to outside programs through the Workflow API and an MCP server. Read it first to see which actors the nine workflow specs share.

Read the workflows in this order

  1. Start with agent-with-tools to see the Agent call Tool components from Chat Input to Chat Output.
  2. Read agent-as-tool to see a second Agent attached as a Tool.
  3. Read mcp-client to see the Agent reach tools hosted on an MCP Server.
  4. Read mcp-server to see a Flow served as a tool on the MCP Server.
  5. Read memory-and-sessions to see the Agent read Langflow Storage by session ID.

1 · Agents talking to agents over A2A

Langflow can publish a flow as an A2A agent that A2A clients discover and call, and a flow can call a remote A2A agent through a calling component. Build it to expose an agent to other systems or to reuse one that lives elsewhere.

Steps

  1. Set LANGFLOW_A2A_ENABLED to true before starting Langflow.
  2. Open a flow that has Chat Input and Chat Output and turn on Serve as an A2A agent in the Agent tab.
  3. Click Save so the status changes to Live and the card and endpoint are served.
  4. Send a message from an A2A client to the JSON-RPC endpoint and read the reply.
  5. In another flow, add the calling component and set Mode to Internal or External.
  6. Connect Chat Input to the Message input and the Response output to Chat Output.

Not in the documentation: The pages do not describe how the Remote A2A agent runs internally or how the caller negotiates with it beyond the URL and the reply. OAuth is not supported for A2A as of Langflow 1.11.x.

2 · A manager agent delegating to other agents

A primary Agent calls a second Agent as a tool, so each specialized agent handles the queries suited to it. Build it when one agent should hand complex or domain-specific work to another model.

Steps

  1. Create a flow from the starter template.
  2. Add a second Agent component and add the API key to both agents.
  3. Enable Tool Mode on the second Agent component.
  4. Edit the tool's actions so the slug and description say what the agent is for.
  5. Connect the second agent's Toolset port to the primary agent's Tools port.

Not in the documentation: These pages do not name the Chat Input and Chat Output components for this flow, and do not describe how the second agent's answer is passed back to the primary agent.

3 · An agent calling tools

A Langflow Agent component receives a chat message and answers it, calling connected tool components when it decides they can help. Build it when a chat flow must search the web, fetch pages or calculate rather than rely only on the model.

Steps

  1. Add an Agent component and select a model from the Language Model dropdown.
  2. Add Chat Input and Chat Output components and connect them to the Agent.
  3. Add Web Search, URL and Calculator components and enable Tool Mode on each.
  4. Connect the Toolset port of each tool to the Tools port on the Agent.
  5. Open the Playground and ask a question that needs a tool, such as a news summary.
  6. Read the tool calls, their input and the raw output in the Playground.

Not in the documentation: The pages do not draw the tool results as a separate arrow back to the Agent; they describe the Playground showing the raw output the agent received.

4 · Pausing a Flow for a Human

Human-in-the-Loop pauses a flow, creates a checkpoint and waits for a human decision. Build it when a step, such as committing code, must be approved before the run continues.

Steps

  1. Add a Human Input component after the code generation steps.
  2. Enter Form Content and keep the Approve and Reject User Actions.
  3. Connect the Approve output to the commit step and the Reject output to an alternate path.
  4. Optionally enable Requires approval on the Git commit tool of the Agent.
  5. Run the flow in the Playground and select an action in the approval pane.

Not in the documentation: The pages do not say that Notify and Listen are part of a human approval gate. They do not name the component that revises a rejected draft, so no revision loop is drawn.

5 · Branching, looping and sub-flows inside a flow

If-Else and Smart Router send a message down one branch, Loop repeats a chain of components for every item in a list, and Run Flow runs another flow as a step. Build them when one linear path is not enough.

Steps

  1. Connect a list such as a CSV file to the Loop component.
  2. Connect the Item port to one chain of components and connect the last component back to the Looping port.
  3. Connect the Done port to the component that receives the aggregated result.
  4. Use If-Else with an operator and match text to send a message down the True or False port.
  5. Use Smart Router with a Routes table and a Language Model to route by category.
  6. Add Run Flow and select the flow to run, or attach it to an Agent as a tool.

Not in the documentation: The pages do not name the component that follows the Positive, Negative or Neutral ports of the Smart Router. The pages say the If-Else component is not compatible with the Loop component, and give no flow between them. The pages do not name the component that receives the Run Flow outputs.

6 · An agent using an MCP server's tools

The MCP Tools component connects an external MCP server to a Langflow Agent so the agent can use the server's tools when answering a prompt. Build it when the agent needs specialized tools such as weather or fetch.

Steps

  1. Register the MCP server in Settings or the MCP sidebar with JSON, STDIO, or HTTP/SSE.
  2. Add the MCP Tools component and select the registered server in the MCP Server field.
  3. Select a tool, or leave it blank to allow all tools.
  4. Enable Tool Mode on MCP Tools and connect its Toolset port to the Tools port of the Agent.
  5. Attach Chat Input and Chat Output to the Agent.
  6. Open the Playground and ask a question that needs the tool.

Not in the documentation: The pages do not state how the Agent and the MCP server exchange messages on the wire.

7 · Flows exposed as tools to MCP clients

A Langflow project has its own MCP server that exposes the project's flows as tools. MCP clients such as Cursor connect to that server and call the tools when generating responses.

Steps

  1. Create a Langflow project with at least one flow that has a Chat Output component.
  2. Select which flows are exposed as tools on the MCP Server tab.
  3. Edit each tool name and description so clients can pick the right tool.
  4. Set the authentication method for the project's MCP server.
  5. Add the server to an MCP client with the JSON snippet or Auto install.
  6. Test the tools in MCP Inspector, then ask the client a question that needs a flow.

Not in the documentation: The pages do not state how the MCP Server runs a flow internally after a tool call arrives. The pages do not draw a direct link between the coding agents of the Langflow MCP Client setting and the project MCP server.

8 · Conversation memory across turns and sessions

Langflow stores chat messages in its database under a session ID, and a flow reads them back by that ID. Build this flow when an agent should remember earlier turns of the same conversation.

Steps

  1. Pass a custom session ID in the API call, or leave it empty to use the flow ID.
  2. Add a Message History component in Retrieve mode at the start of the flow.
  3. Add a Prompt Template with a memory variable and connect the Message History output to it.
  4. Connect the Prompt Template output to the Agent and connect Chat Input to the Agent.
  5. Connect the Agent output to Chat Output.
  6. Add a second Message History in Store mode and connect Chat Output to its Message input.

Not in the documentation: The pages do not show the Session ID as a component with ports; it is a parameter passed in the payload or set in a component's advanced settings. The pages describe the Prompt Template wiring with a Language Model component and say an Agent can be used instead.

9 · Running a Flow from an Application through the API

An external application calls the Workflow API with a flow ID and an input, and gets the result back in one response, as a stream of events, or later from a queued job. Build it when a chatbot, website or script must run a Langflow flow.

Steps

  1. Open the flow, click Share, select API access and copy the snippet for your language.
  2. Set the Langflow API key in the x-api-key header.
  3. Send a POST request to the Workflow API with the flow_id, the input_value and a mode.
  4. In sync mode, read the answer from output.text in the response.
  5. In stream mode, read the events from the stream until the run ends.
  6. In background mode, poll the status endpoint with the job_id until the status is completed.

Not in the documentation: The pages do not state how the sync response travels back from the Workflow API to the application as a separate step, so no return arrow is drawn for it.
